## 1. Что это за проект

Две разные вещи в одном репозитории.

**MVP** (`src/clinic_siting/`, `scripts/`) — исходный студенческий пайплайн:
модель ставит клетке `wealth_score`, скоры сортируются, топ объявляется
ответом. Работает, защищён, трогать без просьбы не надо.

**SETO** (`seto/`) — стенд сравнительного эксперимента по пропозалу v2 для
лаборатории ИИ в медицине. Вопрос: какое качество размещения даёт MVP против
простых геометодов и что вносит каждая часть системы — оптимизатор, данные о
населении, оценщик VLM, изображение. Вся новая работа идёт здесь.

Это **не продукт**. Стенд не должен «выбирать хорошие места» — он должен
честно мерить и сравнивать варианты на одних данных и одних ограничениях.
Отсюда почти все решения в коде: один расчёт метрик на все варианты, запрет
подмены одного варианта другим, фиксация протокола.

Первичных метрик две: ΔCov_T для качества размещения и М2 (ошибка замещения и
доля захвата) для вклада изображения. Определения — `docs/METRICS.md`.

| вариант | что это |
|---|---|
| A | 1000 случайных допустимых наборов, нижняя планка |
| B | P-median, вес — всё население P |
| BN | P-median, вес — нуждаемость N, эталон для М2 |
| M | максимальное покрытие, верхняя граница главной метрики |
| C | P-median, вес P·(1 + α·ŝ), скор модели по тексту |
| D, D10 | то же, скор модели по снимку 25 см и 10 м |
| CN, DN | то же, что C и D, но поверх N, описательно |
| E | GIS-AHP по Dutta et al., выбор по пригодности |
| EN | E с критерием нуждаемости вместо трущоб и бедности |
| EP | пригодность EN входит в вес того же P-median |

Пропозал лежит **вне репозитория**, уровнем выше:
`../Пропозал_геоаналитика_эксперимент_валидация_2.pdf` и текстовая копия `.txt`
рядом. `docs/TODO_V2.md` и `docs/MADRID_DATA.md` лежат в папке `docs/`, но в git их
нет: документы рабочие, их не коммитим. Если файлов нет на диске, спроси у Кирилла,
не выдумывай содержание. Старые пропозалы — в `project x/_archive_old_proposals/`.

## 3. Как запустить

```bash
python -m seto doctor madrid                        # конфиги, git, данные, ключ, зависимости
python -m seto prepare-city madrid                  # сетка, население, граф, площадки; 2,5 минуты
python -m seto step2 madrid <папка prepare-city>    # A, B, BN, M, E, EN, EP и М2 при всех k; 43 минуты
python -m seto ahp-stability madrid <папка prepare-city>   # устойчивость E; 3 секунды
pytest tests/                                       # 562 теста, около 2 минут
```

С моделью. Сервер внутренний, отвечает из сети университета. Если включён VPN «на весь
трафик» (Happ), он забирает маршрут: тогда в окружение команды —
`SETO_BIND_SOURCE_IP=<адрес Wi-Fi>`, `.env` не трогать. До заморозки это разработка:

```bash
python -m seto score-sample madrid <папка prepare-city> --mode text --cells 1
python -m seto score-sample madrid <папка prepare-city> --mode image --cells 1
python -m seto run-city madrid --with-image         # C, D, D10, CN, DN и отчёт; 1 ч 20 мин без кэша
python -m seto m4 madrid <папка run-city> <папка run-city>/scores_image.parquet
python -m seto step2 madrid <папка run-city> --scores <папка run-city>   # захват C, D, D10
```

Ответы модели кэшируются в `C:\seto-data\cache\vlm\`: повторный `run-city` с тем же
промптом идёт минуты, а не час.

Результат считается только после заморозки и только с `--protocol`. Ответы модели
берутся из кэша, если промпт и снимки те же:

```bash
python -m seto freeze-protocol                      # в папку protocol/, она вне git
python -m seto run-city madrid --with-image --protocol protocol/protocol.json
python -m seto step2 madrid <папка run-city> --scores <папка run-city> --protocol protocol/protocol.json
```

Окружение — `pip install -r requirements.txt`, Python 3.11. `pulp` ограничен
`<4`: в 4.x сменился API, и решатель ILP падает с `TypeError`. На этой машине
интерпретатор — `.venv/Scripts/python.exe`.

Нужно в `.env` (файл в `.gitignore`, в индекс не попадает):

```
MODELS_BASE_URL=http://10.100.11.205/v1
MODELS_API_KEY=<ключ внутренних моделей Иннополиса>
SETO_DATA_ROOT=<путь вне облачной папки>
SETO_BIND_SOURCE_IP=<ip Wi-Fi>     # только если VPN забирает весь трафик
```

Шаблон — `.env.example`.

`SETO_DATA_ROOT` вынесен из OneDrive сознательно: там десятки гигабайт, а
синхронизация тормозит каждую запись. Сейчас это `C:\seto-data`. Внутри:
`raw/<город>/<дата>/` только на чтение, `runs/<город>/<run_id>/` никогда не
перезаписывается, `cache/vlm/` — ответы модели, `human_log.csv` — журнал времени.

Срез Мадрида — `raw/madrid/2026-10-28/`, дата записана в `madrid.yaml`
(`snapshot_date`). Все команды, кроме `acquire`, берут её из конфига. **`acquire` без
`--snapshot-date` берёт сегодняшнюю дату** и начнёт новую папку, поэтому при дозагрузке
дату надо передавать явно.

Всего 24 команды CLI, все реализованы (`PLANNED` пуст). Городов в конфигах три:
`madrid` — рабочий, `moscow` и `luzern` остались с прошлых этапов, все три с ролью `dev`.

## 4. Красные линии

Это не стилистические предпочтения. Нарушение любой строки делает результат
эксперимента недействительным, а не просто хуже.

**Модель не считает числа.** VLM даёт только подоценки видимого (тип жилья,
эпоха, доля жилья, стройка, назначение, достаток) и одну фразу обоснования.
Население, расстояния, спрос, конкурентов считает код. В промпте запрет
считать стоит явным текстом, не убирай его.

**Скор получается из подоценок по заранее заданному правилу.** Модель не
спрашивают про нуждаемость. Правило лежит в `global.yaml: score_rules`, одно на все
города, и не подбирается по данным, даже если данные просят. Доля жилья в него не
входит: иначе D − C смешала бы «видит ли модель нуждаемость» с «поправляет ли модель
население».

**Скор входит ровно одним способом.** `w_i = P_i · (1 + α · ŝ_i)` —
множитель веса спроса, и всё. Он не фильтрует площадки, не штрафует их, не
участвует в ограничениях. `ŝ` нормируется по всем клеткам города, включая пустые.
Если появится второй канал влияния, разница D − C перестанет означать вклад
изображения. Единственное исключение в пропозале — частный сценарий, он отложен.

**Точку и тип выбирает оптимизатор, не промпт.** P-median и максимальное
покрытие. Никогда не возвращай «модель выбрала место».

**Один код метрик на все варианты.** Если для какого-то варианта метрика
считается отдельной функцией, сравнение мерит разницу реализаций.

**Варианты не подменяются.** Нет снимков — вариант D получает статус
`missing_external` и отчёт пишет «нет данных». Подставить вместо него C —
значит обратить главную разницу в ноль по построению. Частичный D тоже
запрещён: нет снимка хотя бы одной клетки — D не считается (`_load_images`).
То же для BN и EN: без нуждаемости они «нет данных», а не копия B и E.

**Импортированное решение E не правится.** Нарушение ограничений — отказ с
причиной. E теперь наша реконструкция, но приём внешнего решения в коде остался.

**Среднее `A_i` по 2SFCA не выводится.** При одинаковом k оно равно
ΣS_j / ΣP_i и от размещения не зависит. Это тождество используется как тест
корректности с точностью 1e-9 — не удаляй тест, увидев «странную» проверку.

**Расстояния только по сети.** Ни в решениях, ни в метриках, ни в
ограничениях нет расстояний по прямой.

**Метрика не строится по оценке самой модели.** Группы и веса — только из внешней
статистики. Эталон М4 модель не видит: доход не входит в таблицу признаков.

**Протокол заморожен — параметры не меняются.** После `freeze-protocol`
правка T, k, α, правил перевода или r выглядит подгонкой под результат. `run-city` и
`step2` с `--protocol` сверяют коммит, параметры, правила города и данные у города с
любой ролью. Результатом считается только прогон, в манифесте которого есть
`protocol.json`. Настоящей заморозки ещё не было, см. раздел 8.

## 5. Ловушки, которые уже стоили времени

Каждая из них сначала выглядела как что-то другое. Не повторяй.

### Мадрид: данные

**GHS-POP на Мадриде систематически ошибается.** Растр завышает город на 10 % (3,88 млн
против 3,47), занижает бедный юг, завышает богатый север и селит около 14 тысяч
человек в аэропорт. Поэтому сумма по участку берётся из падрона.

**Внутри участка пиксели GHS селят людей на склады.** Отсюда квартиры кадастра
(`population.registry_by_dwellings`). Клетку сменили 5,41 % жителей, но вывод о М2 при
этом поменялся местами. Разницы в несколько единиц на 1000 там, где кадастра нет,
нельзя считать сигналом.

**«Здание» кадастра — это участок застройки.** Комплекс может лежать в четырёх участках
падрона. Контур режется по границам, точкой ставить нельзя: один такой комплекс давал
749 жителей без единой квартиры в соседнем участке.

**`start_date` в OSM Мадрида почти пуст:** 13 жилых зданий из 69 180 (в Москве 37 %).
Год берётся из кадастра. У перестроенного дома там может стоять год перестройки, поэтому
часть промахов М4 будет ошибкой эталона.

**Коды муниципалитета разные:** 28900 в кадастре и 28079 у INE. Город один.

**Вход «25 см» на деле 0,56 м на пиксель.** Снимок 2000×2000 сжимается до 896×896, это
вход модели. В отчёте и протоколе это надо раскрывать, отступление записано в конфиге.

**Sentinel-2 берётся настоящий, а не огрублённый PNOA.** На Люцерне они меняли решение
по-разному (`docs/RESOLUTION_STUDY.md`). Файл TCI упирается в потолок яркости на светлом
грунте: больше половины площади у 39 клеток с 371 жителем. TCI оставлен сознательно.

**Исходный файл кадастра нельзя передавать** ни в каком виде. Он лежит только в
`C:\seto-data`, в git его нет, другой участник качает его сам через `acquire`. Признаки
по клеткам передавать можно. Наш продукт нельзя называть «кадастровой картографией» и
«кадастровой информацией», D.G. del Catastro указывается как автор и владелец данных.

### Чтение результатов

**M в `metrics.csv` найден только при T = 15.** В строках T = 10 и 20 это те же точки,
просто пересчитанные. Пропозал требует искать M заново под каждый порог. На этом я
ошибся дважды: на Москве и на Мадриде, где вывод «EN лучший при T = 10» оказался неверен
(EN +0,96, пересчитанный M +1,90 при k = 2). Сравнение по порогам — `sensitivity` или
таблица в `docs/RESULTS.md`, прогон 8.

**Ноль у EN при T = 15 — не сбой.** Его площадки стоят в 13–15 минутах от сети, новых
жителей в 15-минутной зоне там нет.

**Порог шума 0 при k = 1 не значит «шума нет».** Все 200 шумовых решений совпали с B,
потому что B при малом k очень устойчив. При этом смена раскладки жителей меняет решение
сильнее, чем шум ±10 %.

**Захват 100 % может получиться случайно.** Случайный скор при k = 1 и 5 отыграл весь
потолок, а при k ≤ 2 сохранил решение B в 80–86 % случаев. Порог шума этого не ловит:
шум P_i ±10 % гораздо уже канала скора (вес × 1…2). Совпадение D с B при малом k ничего
не говорит о модели.

**`metrics.equals(...)` между прогонами может дать False.** У Тейля разница 1e-16, это
округление. Сравнивай с допуском.

### Модель и кэш

**Подставные ответы модели нельзя пускать в настоящий кэш.** Проверки без сервера
гоняются только в отдельном `SETO_DATA_ROOT` или в памяти. Попавшая в `cache/vlm/`
подделка потом выглядела бы как настоящий ответ.

**Кэш ответов модели был привязан к текущей папке.** Из-за этого один прогон
заново вызвал API 2064 раза. Путь теперь `data_root(cfg) / paths.vlm_cache /
mode`. Проверь это, если увидишь неожиданные вызовы API: сервер общий, и
расходовать его надо экономно.

**VPN `happ-xray` перехватывает маршрут до внутреннего эндпоинта.** Создаёт
адаптер `172.19.0.1` и подменяет DNS. Правильное решение — исключить
`10.0.0.0/8` из туннеля; в коде есть обход `SETO_BIND_SOURCE_IP`.

**Каталог `/v1/models` ≠ работающие модели.** Это список роутера LiteLLM.
Часть моделей отдаёт 500 или 404. Перед прогоном нужен health-check
выбранной модели.

### Заморозка

**Файлы протокола нельзя класть в git-дерево.** Неотслеживаемый файл делает дерево
грязным, а коммит протокола меняет сам коммит, и сверка откажет в обоих случаях. Поэтому
папка по умолчанию `protocol/` стоит в `.gitignore`. `docs/protocol/` для этого не годится.

**После заморозки дерево должно оставаться чистым до конца прогонов.** Любая правка
отслеживаемого файла, даже документа, и любой новый коммит дают отказ.

**Папки, сделанные до заморозки, не годятся.** `step2 --protocol` проверяет манифест
папки подготовки и папки скоров: тот же город, тот же срез, коммит протокола, чистое
дерево. Прогон 8 под это не подходит, подготовку надо повторить. Проще всего взять папку
`run-city --protocol`: она содержит и подготовку, и скоры.

### Код и инструменты

**`coo_matrix` суммирует дубликаты рёбер.** Две параллельные дороги между
одними узлами давали сумму времён вместо минимума — бессмыслица. Решено
`_keep_minimum()` в `routing/graph.py`. Если будешь строить граф иначе,
проверь это первым делом.

**Дейкстра со всех источников сразу не влезает в память.** Нужно
`источники × число узлов × 8 байт`. В `routing/matrix.py` стоит разбиение
на чанки по 256 МБ. Не убирай, «чтобы было проще».

**Валидатор нельзя трогать до проверки границ.** Обращение к матрице до
проверки индексов давало `IndexError` вместо внятного отказа. Сначала проверяются
все индексы, потом матрица.

**ILP с big-M для p-median даёт неверный ответ.** Закрытые площадки
перестают связывать, решатель открывает бесполезные точки. Переписано на
классические переменные назначения. Поймал игрушечный тест «ILP совпадает с полным
перебором при k = 2» — `tests/test_seto_variants.py`. Этот тест и есть страховка.

**OSM хранит школы и больницы полигонами, а не точками.** Выборка только по
точкам дала 9 школ вместо 125. Нужны точки И полигоны. Но при склейке
нельзя брать пересечение колонок — так однажды обнулились транспортные
остановки (1141 → 0). Берётся объединение колонок, есть регресс-тест.

**`make_valid` возвращает GeometryCollection.** 6 зданий из 15948 приходили
с болтающимися линиями. `_polygons_only()` их отрезает.

**`building:levels = 0` — это не этажность.** Маппится в NA.

**`union_all` по 200 тысячам зданий вешает машину.** Доля застройки
считается через overlay и `dissolve` по клеткам — 68 секунд вместо вечности.

**`load_dotenv()` внутри функции ломает тестируемость.** `.env` всегда
перебивал конфиг. Вызов стоит на импорте модуля `settings.py`. Модуль называется
`settings.py`, а не `config.py`, потому что рядом есть папка `config/`.

**OneDrive не виноват.** Я однажды ошибочно решил, что медленный импорт — это
облачные заглушки файлов. Настоящая причина — компиляция байт-кода: удаление

`compileall`. Не ищи несуществующую проблему синхронизации.

**pandas с бэкендом Arrow уводит `.str.contains` в RE2,** где `\w` не

## 5а. Тонкости оценки, которых не видно из формул

Формулы — в `docs/METRICS.md`. Здесь то, что меняет чтение результата.

**Сила скора ограничена.** При α = 1 вес клетки растёт не больше чем вдвое
(`P ≤ w ≤ 2P`), а клетка без жителей получает вес 0 при любом скоре.

**Скор пока одна ось.** Правило `age` переводит только эпоху в 3, 2, 1 и 0 баллов,
«не определить» даёт 1,5. На данных это ступенька, а не наклон: доля 65+ около 21 % во
всех эпохах до 2000 и 8,6 % после 2000. Правило оставлено как зафиксировано (Д20).

**Текст варианта C не знает о поликлиниках и населении.** В описании клетки
есть застройка, эпохи из кадастра, школы, магазины с брендами сетей, остановки,
зелень — но нет ни числа жителей (оно уже в `P_i`), ни существующих центров. Версия
шаблона 1.1. В Мадриде у C почти полные годы, в Москве 37 %: сравнивать силу C между
городами надо с этой оговоркой.

**М4 по эпохе считается только для D:** текст C сам содержит год. «Не определить»
считается промахом, иначе отказ от трудных клеток поднимал бы каппу. Модель, которая
всегда отвечает «1955–1975», совпала бы с эталоном в 40,9 % клеток при каппе 0.

**Сбой модели → медиана.** Клетка без ответа после одного повтора получает
медианный скор города (`imputed`). Если таких больше 5 %, вариант в городе
неуспешен. Признак вне списка — не сбой: он становится «не определить», остальные
признаки остаются, исходное значение — в `off_list` (Д24). Без этого 6,5 % жителей D
получали медиану из-за слова «смешанное» в назначении клетки. Все причины сбоев
прогона — в `vlm_failures_<режим>.txt`: в отчёт попадают только первые 20.

**Кэш не видит параметров вызова.** Ключ — клетка, модель, хеш промпта,
хеш входа. `temperature`, `seed`, `max_tokens` в ключ не входят: после их
смены старые ответы берутся из кэша. Смена модели кэш обходит. Наборы снимков делят
один кэш: в ключе байты снимка, они не смешаются.

**Решатель.** B, C, D максимизируют выигрыш `Σ w_i · max(0, t_i^E − t_ij)`,
это то же, что минимум `Σ w_i · t_i(S)`. Все времена ограничены
`t_max = 60` мин. При k ≤ 2 перебираются все допустимые пары — оптимум
точный. При k = 5 и 10 — эвристика обмена с 20 стартов, на Мадриде сверена с ILP: те
же наборы у B и BN, та же цель у M. Ничья при переборе — меньшая пара индексов.

**E не оптимизирует, а ранжирует.** Поэтому D − E смешивает «снимок против критериев» и
«оптимизатор против ранжирования». Читать её надо рядом с D − EP. Решение E определяет
схема классов (77–100 % разброса), а не веса (меньше 8 %).

**Допустимость зависит от разметки OSM.** Доля «жилой и общественной»
застройки считается только по зданиям с типом из `data/features.py`.
На Мадриде тип есть у 57 % зданий, `building=yes` — 39 %. Порог 5 % отсёк 1993 клетки
из 2626. Препятствие отсекает клетку, только если занимает от 50 % площади.

**Граница города не обрезает ничего.** Сетка — все клетки, касающиеся границы, целиком.
На Мадриде таких 410 из 2626. Площадка может попасть в клетку, почти целиком лежащую за
границей: `inside_share` в правиле допустимости не участвует.

**P10 и P25 по 2SFCA равны нулю, пока `Cov_T` < 75 %.** На Мадриде `Cov_15` = 86,5 %,
поэтому нулевым остаётся только P10, а P25 почти не различает варианты: при k = 2 он
1,5–1,6·10⁻⁵ у всех. Работает «доля ниже `A_0`».

**A считается при том же k, что остальные;** процентиль варианта в A — строгий
(«доля наборов хуже»).

**Совпадение C с B** даёт статус `skipped_duplicate`, но метрики C всё равно
считаются и попадают в таблицу. Совпадение BN с B, CN и DN с BN — результат, а не
дубликат.

**Знак разниц.** Проверяемый вариант слева: M − B, D − C. Порядок задаёт `CHAIN` в
`experiment/evaluate.py`. В `run3_report.md` пары идут по алфавиту, там «B − C = −0,10»
значит C − B = +0,10.

```
seto/
  acquire/    загрузка сырых данных, чтение PBF через GDAL-драйвер OSM

  scoring/    промпт, вызов модели, кэш, правило перевода, веса спроса
  variants/   решатели A/B/M/C/D, GIS-AHP, приём внешнего E
```

Замок в `imagery/tiles.py` не мешает Мадриду: снимки идут через `imagery/wms.py` и

2ГИС массовая выкачка и обработка нейросетью запрещены лицензией.

Параметры только в конфигах. Не хардкодь границы, размер клетки, имя модели,
веса, порог T, k и α — читай из конфига. Всё мадридское — в
`config/cities/madrid.yaml`: позже добавятся другие города.

## 9. Как работать с Кириллом

Кирилл — студент первого курса, команда из трёх человек, проект будут читать и
защищать. Код должен быть понятным, а не умным. Все ответы — по-русски и простым языком.

- **Один блок TODO_V2 за раз.** Внутри блока деление на задачи оставь для себя. Отчёт
  присылается только о целом блоке: какая была проблема и как её исправили, простыми
  словами. Следующий блок начинается после ответа Кирилла.
- **Коммит — только целый блок.** Каждый блок — один коммит. `docs/MADRID_DATA.md` и
  `docs/TODO_V2.md` не коммитятся. Документы, которые уже в git (`RESULTS.md`, `METRICS.md`
  и другие), идут в коммит своего блока. `git push` не делать без просьбы.
- **Проверки важнее бумаг.** Сначала проверь на настоящих данных, потом записывай.
- **Сначала на одной клетке, потом на всех.** Особенно вызовы модели: сервер общий.
- **Не выдумывай API и форматы данных.** Не уверен — напиши код, который
  печатает формат, посмотри, и только потом парси.
- **Не отклоняйся от плана молча.** Если шаг не работает: остановись,
  объясни простыми словами что именно не сработало, предложи один-два
  варианта с плюсами и минусами, спроси. Отклонение — только после
  подтверждения.
- **Если альтернатива нарушает красную линию из раздела 4 — не предлагай её**,
  ищи другую.
- Сообщения от имени Кирилла (товарищу, руководителю) не отправляй без явного согласия.
- Скачивание файлов — с согласия, с указанием имени, источника и размера. Скачанные
  архивы — в отдельную новую папку.
- Комментарии по-русски там, где объясняешь «почему», а не «что».
